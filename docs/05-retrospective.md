# 05 复盘

## 最难的问题

最难的问题是协调重复提交与排期变化：同一请求应始终对应一份草稿，同时又要根据最新占用情况更新建议。

最初采用幂等键直接返回已有草稿。进一步验证发现，当 18:00 与 19:00 的占用情况互换时，已有建议也需要重新计算。最终将需求身份与排期方案分开管理：需求指纹和草稿 ID 保持稳定，每次执行重新读取资料、审核规则、查询时段，再通过事务更新原草稿。验证时同时核对建议时段、原始要求、草稿 ID 和数据库行数。

第二轮审查进一步明确了三个独立状态：最新操作是否成功、数据库实际保存了什么、当前审核依据是否仍然有效。通过分别记录这些状态，系统能够准确呈现保存失败、历史草稿保留和资料变化后的重新审核过程。

## 实际学习与设计收获

这次实现最有价值的收获，是把业务目标转化为可执行、可验证的约束。

- **明确模型与程序的职责。** 模型根据工具反馈选择补查、调整时段或结束；业务代码负责确认权限、风险规则、冲突检查和数据唯一性。
- **细化业务状态。** 待确认建议与确认时段分别存储，最新保存结果与持久化记录分别展示，使每个状态都有明确含义。
- **管理证据的时效性。** 审核结论绑定素材与规则的内容摘要，资料变化后触发草稿失效和重新审核。
- **建立清晰的资料合并规则。** 归档用于补充缺失信息，合并时保留风险信号，对未知风险和矛盾信息发起人工复核。
- **同时验证安全性与可用性。** 对抗测试检查越界动作，正常案例检查核心流程，二者共同约束修复结果。
- **用实际反馈验证 Agent。** 更换占用时段、注入工具失败、调整资料内容，再检查模型的后续动作，能够直接观察决策循环是否有效。

工程接入也提供了具体经验：先检查本地环境和接口可用性，再确定模型适配方式。通过接入现有 DeepSeek 配置，完成了真实模型调用、工具反馈和运行记录的完整验证链路。

## 下一步

1. 增加显式确认、撤销和修订命令，完善草稿生命周期，并自动归档被替代的建议。
2. 引入远端资料版本与更新通知，补齐草稿修改历史和审核事件记录。
3. 将离散时段扩展为时间区间，支持不同素材时长、跨频道资源和批量排期。
4. 扩大真实模型评估样本，覆盖不同措辞、连续追问、提示注入和多次独立运行，统计完成率与工具调用成本。
5. 整理业务规则、关键决策与 Trace 的对照示例，提高项目复现、问题定位和方案讲解的效率。
