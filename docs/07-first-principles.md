# 07 从第一性原理推导题解

## 先确定系统究竟承诺什么

题目不是要求“调用四个工具”，而是让内容团队得到可确认、无冲突、保存结果可信的排期草稿。一次调用完成，不等于业务成立；一个旧草稿存在，也不等于本次修改保存成功。

系统需要回答五个独立问题：素材是什么，证据是否足够，当前规则是否允许，用户是否授权这个时间，建议是否真实持久化。这些事实不能互相代替。

## 由目标推出不变量

| 原始目标 | 必要条件 | 程序如何保证 | 不能替代的证据 |
| --- | --- | --- | --- |
| 审核可靠 | 资料完整有效，风险被识别 | 字段类型校验、未知风险转人工、已知阻断风险不能被覆盖 | 模型自称“无风险” |
| 确认边界 | 硬性时段或明确确认的时段才可成为确认草稿 | 不可变请求；模型不能传确认参数；硬性原时段仍可用时不能擅自换时段 | 模型建议替代时段 |
| 没有冲突 | 选择、保存、最终返回时分别核对可用性 | 查询快照、保存重查、SQLite 唯一约束、返回前复核 | 曾经可用的查询结果 |
| 审核仍有效 | 审核依据和当前资料、规则一致 | source_revision 绑定证据，变化后重新读取与审核，旧草稿失效并释放占位 | 旧版本审核通过 |
| 保存可信 | 最新写入结果与持久化事实均可核对 | save_status 表示最新尝试；persisted_draft 单独读取历史/当前记录 | 旧草稿存在或模型说保存成功 |
| 重复安全 | 同需求不新增第二份草稿，同 ID 不换需求 | 请求进入时绑定 ID；需求指纹、事务和唯一索引 | 只在成功保存时记录请求 ID |
| 有限执行 | 失败时可停止并交代缺口 | 模型调用上限；错误与未完成状态 | 无限制自动重试 |

可确认草稿需要同时满足：**当前资料有效 ∧ 当前审核通过 ∧ 用户授权该时段 ∧ 时段无冲突 ∧ 数据库存在相符草稿**。任何一项没有证据，都不能报告“排期已确认”。发布还需要独立权限与系统接入，本项目没有发布动作。

## 未知、矛盾与变化分别处理

- 缺失或格式错误：证据不足，补查或请求补充，不能按无风险处理。
- 未知风险标签：规则尚未覆盖，交由人工复核，不能因为“不在黑名单”就放行。
- 主素材与归档矛盾：主素材建立素材身份，归档只补缺项；已知事实不被静默覆盖，风险标签累积，矛盾转人工。主素材已明确未授权时仍然阻断。
- 资料或规则变化：旧审核证明失效。草稿保留历史，但确认时段被撤销；只有新证据重新审核通过后才可恢复。
- 保存失败但旧草稿仍在：本次 save_status=failed，task_status=failed；旧内容在 persisted_draft 中保留，不伪装成最新修改成功。

资料版本用规范化内容摘要表示，覆盖该素材主资料、归档和审核规则。它检测的是内容差异，不是假装来源带有真实机构签章。归档发生无关变更也可能保守地触发复核，这是小规模本地实现的明确取舍。

## 为什么需要模型，以及哪些部分不能交给模型

模型的价值在于看到工具结果后选择下一步：补查、查替代时段、重新审核、请求确认或结束。它可以选择不同合法顺序；本程序不把固定重试或预写日志包装成真实决策。

但模型不能成为授权、事务或事实来源。确认边界、风险阻断、版本失效、幂等、占位与最终状态由确定性代码保证。即使模型受素材中的提示注入影响，输出发布动作或伪造确认参数，动作校验也拒绝执行。

## 如何证明改进有效

安全性需要“恶意动作不能越界”，可用性需要“正常请求仍能完成”。只把所有请求都拒绝，会通过一些安全断言，却违背用户目标。因此同时运行：正常验收、九个已复现攻击、3,888 条有限动作序列、实际本地 HTTP 重定向测试、真实 DeepSeek 工具反馈循环。

评估不只比较 task_status 字符串，还核对数据库读回、草稿数量、保存回执、原始硬性时间、确认状态和执行预算。对抗测试只能证明已枚举范围内的行为，不能证明任意攻击或生产场景安全。

## 最小范围保持不变

仍然是一个 Python CLI、一个 Agent 循环、四个本地业务工具和一个 SQLite 数据库。新增的是证据与状态约束，没有引入界面、部署、多 Agent 或真实发布。资料身份、用户确认和规则来源在本地环境被视为可信输入；真实多用户授权和跨系统分布式一致性属于后续工作。
