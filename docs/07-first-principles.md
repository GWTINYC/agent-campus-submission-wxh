# 07 从第一性原理推导题解

## 明确交付目标

项目的目标是让内容团队得到可确认、无冲突、保存结果可信的排期草稿。工具调用、审核结论、用户确认和保存结果分别对应业务链路中的不同事实，需要各自验证。

系统围绕五个问题组织流程：素材是什么，资料是否完整，当前规则是否允许，用户是否授权该时间，建议是否已经持久化。

## 由目标推出不变量

| 原始目标 | 必要条件 | 程序如何保证 | 验收依据 |
| --- | --- | --- | --- |
| 审核可靠 | 资料完整有效，风险被识别 | 字段校验、未知风险转人工、保留阻断风险 | 规则检查结果与风险原因 |
| 用户确认 | 时间符合原始要求或明确确认 | 不可变请求、确认字段校验、硬性时段约束 | 原始要求、confirmed_slot 与 effective_slot |
| 时段可用 | 选择、保存、返回时核对可用性 | 查询快照、保存重查、SQLite 唯一约束 | 最新查询和数据库占位 |
| 审核有效 | 审核依据与当前资料、规则一致 | source_revision 绑定，变化后重新读取和审核 | 资料摘要、审核摘要与草稿状态 |
| 保存可信 | 写入结果与持久化事实一致 | 最新尝试与持久化记录分别展示 | 工具回执及数据库读回 |
| 重复安全 | 同需求对应一份草稿，同 ID 绑定同需求 | 入口绑定 ID、需求指纹、事务和唯一索引 | 草稿 ID、行数和需求指纹 |
| 有限执行 | 失败时停止并说明缺口 | 模型调用上限、错误及未完成状态 | 调用计数、stop_reason 和任务状态 |

可确认草稿需要同时满足：**当前资料有效 ∧ 当前审核通过 ∧ 用户授权该时段 ∧ 时段无冲突 ∧ 数据库存在相符草稿**。系统根据这些条件生成草稿状态，发布权限与真实发布接入由后续发布系统承担。

## 未知、矛盾与变化分别处理

- 缺失或格式错误：补查资料或请求用户补充，返回具体缺失字段。
- 未知风险标签：交由人工复核，并记录标签及原因。
- 主素材与归档矛盾：主素材建立素材身份，归档只补缺项；已知事实不被静默覆盖，风险标签累积，矛盾转人工。主素材已明确未授权时仍然阻断。
- 资料或规则变化：旧审核证明失效。草稿保留历史，但确认时段被撤销；只有新证据重新审核通过后才可恢复。
- 保存失败且旧草稿仍在：本次 save_status=failed，task_status=failed，旧内容通过 persisted_draft 展示。

资料版本采用规范化内容摘要，覆盖该素材主资料、归档和审核规则。每次操作核对摘要，内容变化后触发重新审核。当前粒度为整份资料，后续可细化到字段级依赖，减少无关更新带来的复核。

## 模型与业务程序的分工

模型根据工具返回选择下一步：补查、查询替代时段、重新审核、请求确认或结束。每次决策都接收前一步观察，形成可追溯的工具反馈循环。

业务程序负责确认权限、风险阻断、版本失效、幂等、占位和最终状态。动作校验会拒绝发布动作、额外确认参数等越界请求，工具返回和数据库记录提供事实依据。

## 如何证明改进有效

验证同时覆盖安全性与可用性：正常案例检查业务完成，恶意动作检查约束执行。测试组合包括正常验收、九个定向攻击、3,888 条有限动作序列、本地 HTTP 重定向测试和 DeepSeek 真实决策路径。

评估核对 task_status、数据库读回、草稿数量、保存回执、原始硬性时间、确认状态和执行预算。不同测试分别验证状态约束、存储一致性和模型决策。

## 实现范围

项目由 Python CLI、Agent 循环、四个本地业务工具和 SQLite 数据库组成。当前使用可信本地输入表达资料身份、用户确认和规则来源；后续可扩展多人授权与跨系统一致性管理。
